# Index 18 - NPC_DEFINITIONS

**Format:** fully-understood  
**Capability:** read-write-no-tests  
**Effort:** small

## What it is

NPC type definitions, one per NPC id. Group (folder) = npcId >>> 7, file within the group = npcId & 0x7F, so 128 NPC ids per group - settled by the client, not inferred: Class301.method3538 calls `aJS5Archive_2504.getChildFromFolder(i_5_ >>> 7, Class163.method2520(i_5_, ...))` (Class301.java:207-208) and Class163.method2520 is `return i & 0x7f` (Class163.java:143). Index 18 is opened at InterfaceSettings.java:174 (`openFileStore(-90, false, 1, 18)` -> Class234.aJS5Archive_1751) and handed to the NPC provider `Class301` at InterfaceSettings.java:277-278. One file = one record = one `Class141` instance, a self-delimiting opcode stream: read an unsigned opcode byte, read the payload that opcode number implies, repeat until a 0 terminator (Class141.method2297, Class141.java:675-695, dispatching to method2293 at :283-607). There is no length prefix and no field table on disk, so the opcode payload sizes ARE the format. Measured in this cache: 106 groups, 13,359 definitions (AGENTS.md:292, reproduced by a full walk documented at reference/hydra-637-definitions/npc-opcodes.md:137-147). 51 distinct opcodes actually occur; opcodes 95 and 119 occur in all 13,359, opcode 165 in exactly one (npc-opcodes.md:156-163).

## Gaps

- NOT a missing sweep. Do not build one. The full-index byte-identity sweep already exists and already covers all 106 groups / 13,359 definitions on every run: RealCacheNpcDefinitionTests.AllNpcDefinitions_ReEncodeToTheCapturedBytes (FlashEditor.Tests/Cache/RealCacheNpcDefinitionTests.cs:239-305). The grade is below 'complete' for one reason only: GUI editing is unreachable.
- Wire the NPC grid for editing, which is the whole remaining gap. In Editor.Designer.cs's NPCListView block (around :955-973) add `NPCListView.CellEditActivation = ObjectListView.CellEditActivateMode.DoubleClick;` and `NPCListView.CellEditFinished += NPCListView_CellEditFinished; NPCListView.CellEditStarting += NPCListView_CellEditStarting;`, copying Editor.Designer.cs:593 and :612-613 verbatim. Both handlers already exist at Editor.cs:971 and :1161 and the save path behind them is complete.
- The same wiring is missing on GameObjectListView's activation (it has the handlers at Editor.Designer.cs:1154-1155 but no CellEditActivation), so this is an editor-wide defect rather than an NPC one - fixing NPC alone leaves objects still uneditable.
- Mark the columns that must stay read-only. `npcIdColumn` (Editor.Designer.cs:974-980) has no `IsEditable = false`, and the save path derives archiveId/entryId from `newDef.id` (Editor.cs:982-983), so an edited id would write the record to a different NPC slot and silently overwrite it. Set `npcIdColumn.IsEditable = false` in the same edit.
- A persistence test for the NPC write path. Nothing in FlashEditor.Tests exercises RSCache.WriteFile on index 18. Per CLAUDE.md, verify by reopening the store rather than reading back through the RSCache that wrote it.
- Cosmetic but misleading: RealCacheNpcDefinitionTests.cs:860-862 maps ids as `archiveId * 256 + fileId` with the comment 'NPC ids are packed 256 to an archive, the same mapping GetNPCDefinition uses'. Both halves are wrong - the client uses 128 (Class301.java:207, Class163.java:143) and GetNPCDefinition takes archiveId and fileId separately. It only labels failure messages and calls SetId (which Encode ignores, NPCDefinition.cs:1131-1133), so no assertion is affected, but anyone copying that line into new code gets the wrong addressing.
- No editing surface for the structured fields: options[0..4], the opcode-40/41 recolour and retexture pairs, the opcode-106/118 morph table, the opcode-249 parameter list and the model id list are all decoded and re-encoded but have no editable UI. The grid exposes 13 scalars and no more.

## Notes and traps

Read the gaps list before acting - the enum rung name understates this index badly. The codec side is arguably the best-defended in the repo; the only thing between it and 'complete' is two lines of designer wiring plus an IsEditable flag.

TRAPS:

1. The format is non-canonical in three ways at once, all already handled - do not "tidy" any of them (NPCDefinition.cs:289-306 documents them, RealCacheNpcDefinitionTests.cs:230-237 asserts them). (a) Opcode ORDER is arbitrary: only 127 of 13,359 definitions store opcodes in ascending order, so an encoder with its own fixed order rewrites 13,232 records the moment a user opens one. (b) Opcodes REPEAT: 538 definitions repeat one, 224 of them repeat opcode 95, and the decoder keeps only the last value as the client does - the earlier occurrences exist nowhere but the recorded bytes. (c) ABSENT versus DEFAULT: the packer stores opcode 12 with size 1 and opcode 97 with scale 128, both exactly the client defaults, so "did the file carry this opcode" cannot be inferred from the field value. That is what the `decoded[256]` hit map and the recorded opcode stream (`OpcodeStreamDefinition.Opcodes`) exist for, and why the bare boolean flags (:49-155) are views over the hit map rather than plain fields.

2. Opcodes 30-34 and 150-154 are two spellings of the SAME five option slots and the decoder folds both into one `options` array. An encoder driven by the array alone emits every option twice and breaks byte-identity for the whole index; Encode picks the range from the recorded stream (NPCDefinition.cs:772-795). It also has to re-spell a null option back as the literal "Hidden".

3. Opcode 249 parameters must keep FILE order and DUPLICATE keys. A SortedDictionary reorders 16 definitions and collapses a duplicate key, shortening NPC 13592 by 8 bytes (RealCacheNpcDefinitionTests.cs:637-658).

4. Highest-severity latent client divergence: opcode 162. The 637 client reads ZERO bytes for it (test Class141.java:478, body :537, sets aBoolean1093 = true); our decoder consumes FOUR (NPCDefinition.cs:469-472). No definition in this cache uses 162, so nothing detects it, but a modified cache containing one desynchronises the entire record. Same shape, lower stakes, for opcodes 44, 45, 112, 170-175 and 179 - ours only, no client case, absent from this cache, provenance untraced.

5. Field-name and semantics hazards for anyone building an editor UI on these values, all with citations in reference/hydra-637-definitions/npc-opcodes.md: opcode 101 `contrast` is stored as a FIFTH of the client's working value and the client reads it SIGNED (2,245 occurrences); opcode 100 `ambient` is signed to the client and unsigned to us (3,800 occurrences); opcode 125 `respawnDirection` likewise and the sign genuinely participates in the arithmetic; opcode 128 `movementType` is read and DISCARDED by the client, so the name is unsupported by any evidence; opcode 155's fourth byte is a blend weight, not an opacity, and -1 in the first three is an explicit "skip this channel" sentinel that an unsigned read turns into 255. None of these affects byte-identity - every one is same-size - so no sweep will ever catch a UI that displays them wrongly. The whole family of 16-bit fields where we use signed ReadShort against the client's readUnsignedShort is unobservable in this cache: no 16-bit field anywhere reaches 0x8000.

6. Our decode loop breaks on opcode 255 as well as 0 (NPCDefinition.cs:337); the client breaks on 0 only (Class141.java:685-687). No definition here uses 255.

7. No XTEA on index 18 and no dependency on another index for decoding. The model preview does depend on index 7 (models) and the texture cache, and Editor.cs:1370 silently returns when `_textureCache` is null - the Textures tab work currently in flight can therefore make the NPC preview appear broken when the codec is fine.

8. Naming hazard while editing NPCDefinition.cs: our field `anInt1104` holds opcode 112, but `anInt1104` in the client is the opcode-100 field. Our `anInt1101`/`anInt1090` hold opcode 162, but those are the client's opcode-164 fields. The two numbering sets cannot be cross-referenced by name at all.
