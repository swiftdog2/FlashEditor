# Index 3 - INTERFACE_DEFINITIONS

**Format:** partially-understood  
**Capability:** none  
**Effort:** large

## What it is

Interface (widget) definitions, in the "if3" format. A GROUP is one whole interface/window; a FILE within it is one component of that interface; a RECORD is one component definition. The client settles all three: `InterfaceSettings.java:161` opens index 3 into `Class64_Sub20.aJS5Archive_3697`, `Class94.method916` (`Class94.java:64,72`) installs it as `Node_Sub17_Sub1.INTERFACE_ARCHIVE` and sizes `Class159.loadedInterfaces = new RSInterface[groupCount][]`, and `EntityEnumType.loadInterfaceIfExists` (`EntityEnumType.java:16-79`) fills row `parent` by calling `getChildsInFolder(0, parent)` for the file count and `getChildFromFolder(parent, childIndex)` per component, then `RSInterface.unpackConfig` on each. The component id the rest of the client uses is `ID_TAG = (parent << 16) + childIndex` (`EntityEnumType.java:46`). MEASURED IN THIS CACHE (my own parse of idx255 g3 + idx3 + dat2, script at C:\Users\CJ\AppData\Local\Temp\claude\C--Users-CJ-Desktop-FlashEditor\f188415d-792b-47d7-bdca-e00fd5387036\scratchpad\idx3.ps1): reference table is format 6, version 1131, flags 0x01, declaring 1078 groups over ids 0..1080 (3 ids unused; idx3 itself is 1081 records), all 1078 present in the dat2, 42,256 files total, none empty, largest group 771 files, and every group's file ids are dense 0..n-1 - which is what makes the client's `childIndex == fileId` assumption safe here. Compression: 953 GZip, 125 BZip2, 0 uncompressed. Every group is a single chunk. All 1078 group identifiers and all 42,256 per-file identifiers are non-zero, so index 3 is the rare index that name-hashes both levels; the table consumes to the byte (270,792/270,792). Name recovery verified self-provingly: Java `String.hashCode("loginscreen")` = -2079671019 -> group 744 and `"lobbyscreen"` = 225502146 -> group 906, which are exactly the two names the client asks index 3 for by name at `InterfaceSettings.java:356-358`; `"inventory"` -> group 149. Every one of the 42,256 files starts with byte 0xFF, i.e. all if3, no legacy if1 record anywhere. Component type (byte 1, low 7 bits): 5 (sprite) 13462, 4 (text) 10317, 6 (model) 7009, 0 (layer/container) 6573, 3 (rectangle) 4528, 9 (line) 367; types 1, 2, 7 and 8 do not occur.

## Notes and traps

TRAPS, in the order they will bite.\n\n1. THE VERSION BYTE GATES FIVE BRANCHES AND IS ALWAYS -1 HERE. `unpackConfig` reads `i_2_ = readUnsignedByte()` and maps 255 -> -1 (RSInterface.java:1035-1039). I measured all 42,256 files: every one starts 0xFF, so `i_2_` is -1 for every record in this cache. Consequences: the `i_2_ >= 0` branches at :1067, :1163 (anInt2350), :1279 (anInt2317), :1289-1307 (THE PARAM TABLE) and :1320 (anObjectArray2253) never fire, while the `i_2_ < 0` branch at :1077 (an extra byte on type-0 components) always does. A decoder written from a modern RS3 if3 reference will unconditionally read the param block and desync every record. Follow the client. Keep the dead branches implemented but expect no test to cover them.\n\n2. `contentType` IS A MISNOMER FOR THE COMPONENT TYPE - a textbook "the name is a claim" case. Settled by what the client does with it: 5 reads imageID and sprite fields (:1082-1096), 6 reads mediaID, rotations and zoom (:1098-1146), 4 reads the message string (:1148-1166), 3 reads colour+fill (:1168-1172), 9 reads line width+colour (:1174-1178), 0 reads scroll extents (:1073-1080). Do not name the field from the client's identifier.\n\n3. `RSBuffer.method1186()` IS A 24-BIT UNSIGNED READ, not a smart/variable int (RSBuffer.java:131-135). It is used for the hook/access mask at :1180 and for param keys at :1293 and :1302. Read it as anything else and everything after it desyncs.\n\n4. THE 0x80 FLAG ON BYTE 1 means a name string follows (:1043-1046). Measured: set on 0 of 42,256 components. The branch is dead in this cache - implement it, but no sweep will defend it.\n\n5. PARENT ID IS TRANSFORMED ON READ. 65535 -> -1, otherwise `parentID + (ID_TAG & ~0xffff)`, i.e. the group id is folded into the high half (:1057-1063). The encoder has to undo both, and the 65535 sentinel must survive.\n\n6. THREE HYDRA CLIENT MODS SIT IN THE LOAD PATH AND ARE NOT THE FORMAT. `EntityEnumType.java:40` substitutes group 259 when asked for group 61. `:55-59` rewrites modelZoom and modelOffsetY for group 408 when mediaID is 15285-15289. `:61-63` force-hides mediaID 27167. `RSInterface.java:1252` even leaves a `System.err.println` in the decoder. Port none of them.\n\n7. NO XTEA, ANYWHERE. `getChildFromFolder` passes null keys (JS5Archive.java:203-205) and index 3 is opened with `bool=false` (InterfaceSettings.java:161). Nothing here is encrypted.\n\n8. COMPRESSION IS MIXED AND MATTERS FOR SAVES. 953 GZip groups and 125 BZip2. GZip never re-encodes byte-identically (AGENTS.md: 0 of 96,183), so the project's "a save that changes nothing must write nothing" rule is load-bearing on this index. Every group is single-chunk, so the chunk-major trap does not arise, but `RSArchive.PutFile` must still not collapse the split.\n\n9. DEPENDENCIES ON FOUR OTHER INDEXES, stated by the client itself: `Class94.method916` is handed index 3 together with 13 (fonts), 8 (sprites) and 7 (models) at InterfaceSettings.java:294-295 - type 5 components reference index 8, type 6 reference index 7, type 4 reference index 13, and the 21 hook arrays reference index 12 (CS2). A viewer that renders components needs all four; a codec needs none of them.\n\n10. GROUP IDS ARE SPARSE, FILE IDS ARE NOT. 1078 groups over ids 0..1080 with 3 gaps, but every group's file ids are dense 0..n-1. Enumerate groups from the reference table, never from 0..1080.\n\n11. FREE NAMES, AND THEY ARE ALREADY REACHABLE. All 1078 group hashes and all 42,256 file hashes are non-zero and already decoded and re-encoded by ReferenceTableCodec. `RSReferenceTable.GetArchiveId(name)` works on index 3 today with no new code. A name list run through NameHasher would name interfaces and individual components verifiably - the same self-proving join the track work settled on, and unlike index 6 there is no ordering guess to get wrong.\n\n12. `reference/` HAS NOTHING ON INDEX 3. No opcode table, no field-name map, no prior analysis. The 637 client is the only source, and it is two builds behind the data - so run the exact-consumption sweep before trusting the read order.
