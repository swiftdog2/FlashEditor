# Index 21 - GRAPHICS (spot-animation / "graphic" definitions)

**Format:** fully-understood  
**Capability:** none  
**Effort:** small

## What it is

Index 21 holds the spot-animation ("graphic" / SpotAnim) definition table: the small opcode records that say which model to draw for a graphic effect, which animation plays on it, and how it is scaled, rotated, lit and recoloured. Client proof: `InterfaceSettings.java:177` opens index 21 into `PlayerUpdateMask.aJS5Archive_525`; `InterfaceSettings.java:286-287` hands that archive plus `MODEL_FILE_SYSTEM` (index 7) to `new Class304(...)`. `Class304.method3564` (`Class304.java:118-146`) is the by-id getter: it fetches `getChildFromFolder(Class329.method3711(id), Class314.method3637(id))`, and those two are literally `id >>> 8` (`Class329.java:39-46`) and `id & 0xff` (`Class314.java:11-18`). So a GROUP is a 256-record page, a FILE within it is one graphic id (`id = group*256 + file`), and one RECORD is a `Class107` decoded by `Class107.method1725` / `method1727` (`Class107.java:247-320`). Callers are graphic-effect packets and entities: `PacketParser.java:923,937,1038,1054`, `Particle_Sub3_Sub4_Sub2.java:356,368,414,442`, `Class333.java:65,85`, `Class340.java:76,166`. Measured in this cache (Python JS5 reader over `cache/main_file_cache.dat2`): reference table is format 6, version 276, flags 0x00 (NO name hashes, so records are addressable by id only); 12 groups, ids 0-11; file counts 249,255,253,256,256,253,256,252,256,256,256,158 = 2956 records; max id 2973. Groups 0,1,2,5,7 are sparse (gaps in the file-id list). Every group is a single GZip container with a 2-byte version trailer, and no group is XTEA encrypted. Records are tiny: 4 to 39 bytes, mean 10.6.

## Current capability

Nothing index-21-specific exists. `RSConstants.GRAPHICS_INDEX = 21` (`FlashEditor/Cache/RSConstants.cs:36`) and the display name `"GRAPHICS"` (`:86`) are the ONLY references to index 21 anywhere in `FlashEditor/` - grep for `GRAPHICS_INDEX` across the whole repo returns exactly that one declaration line and no adoption site, which is the pattern CLAUDE.md describes for the 27 index constants with no feature behind them. There is no definition class (`FlashEditor/Definitions/` holds Item, NPC, Object, FloorUnderlay, FloorOverlay, MapSceneIcon, Model, Sprites, Tracks - nothing spot-animation), no GUI tab (`Editor.Designer.cs:40-148` declares Console, tabPage1, tabPage2, ItemEditorTab, SpriteEditorTab, NPCEditorTab, ObjectEditorTab, InterfaceEditorTab, ModelViewerTab, TextureViewerTab, MapEditorTab, TrackEditorTab), and no test names it. The generic raw-container browser is not a fallback either: `Editor.cs:524-563` only populates `ContainerListView` under `case RSConstants.META_INDEX`. What DOES cover index 21 is the index-agnostic transport sweep - `RealCacheConformanceTests.Containers_PreserveTheirPayloadAndHeaderAcrossReEncode` (`FlashEditor.Tests/Cache/RealCacheConformanceTests.cs:167-202`) and `Archives_ReEncodeToTheCapturedPayloadBytes` (`:217+`) iterate `_cache.TableIndexes` and `ArchivesToExamine(table)`, and since index 21 has 12 groups against `SampleArchivesPerIndex = 250` (`RealCache/RealCacheFixture.cs:24,125`) ALL 12 groups are swept on every run, sampled or FULL=1. So the group unpack/repack and container layer for index 21 are byte-identity proven; the record format inside them is not touched by anything.

## Notes and traps

Measured facts from a standalone Python JS5 reader run against the read-only cache (no repo file touched, nothing built). All 2956 records decode cleanly with the 637 client's opcode table and consume their payload EXACTLY - 2956 of 2956, zero unknown opcodes, zero trailing bytes, zero empty records. So the 637 client is a complete and correct reference for this index in 639: no format drift, and no 639-only opcode of the kind that item opcode 131 represents.

Opcode histogram over all 2956 records: 1 x2956, 2 x2860, 4 x91, 5 x89, 6 x20, 7 x1186, 8 x823, 10 x158, 40 x488. Opcodes 9, 11, 12, 13, 14, 15, 16 and 41 (retexture) occur NOWHERE in this cache. Implement them anyway from the client - they are unreachable and therefore undefended by any sweep, exactly like the reference-table branches CLAUDE.md says to keep.

TRAPS, in order of how much they will cost:

1. OPCODE ORDER IS NOT CANONICAL, and this index is one of the worst offenders. 442 of 2956 records store their opcodes in non-ascending order. The very first record, graphic id 0, is one of them. The distribution: (1,2,8,7) x227, (2,1) x69, (2,1,7,8) x45, (1,2,8,7,40) x40, (1,2,8,7,10) x21, (2,1,10,7,8) x9, (1,2,7,8,4,5) x6, (1,2,4,5,7,8,6) x6, (1,2,8,7,4,5) x5, (1,4,5,2) x4, (1,7,2) x4, plus 6 more shapes, 47 distinct sequences in all. A decoder that writes opcodes back in a fixed ascending order fails byte identity on 442 records - roughly one in seven. Use `DecodedOpcode` and replay the recorded sequence, the same mechanism the floor and terrain codecs use.

2. ABSENT VERSUS DEFAULT, confirmed present. `Class107`'s constructor (`Class107.java:83-92`) defaults scaleXZ=128, scaleY=128, ambient=0, contrast=0, rotation=0. One record stores opcode 4 with the literal value 128, 17 records store opcode 7 with value 0 and 31 store opcode 8 with value 0 - all of them writing the exact value the default would have produced. "Did this record store this field" cannot be inferred by comparing the decoded value to the default; it has to be recorded at decode. The `DecodedOpcode` list does this for free.

3. Opcode repetition does NOT occur here - zero records repeat any opcode. Do not weaken the `DecodedOpcode` design on that basis; it costs nothing and CLAUDE.md's rule is to assume non-canonical until a sweep says otherwise.

4. No name hashes. Table flags are 0x00, so no group or file in index 21 carries an identifier. Graphics can only ever be listed by numeric id; there is no name to recover, unlike index 6.

5. Sparse file ids. Groups 0, 1, 2, 5 and 7 have gaps (249, 255, 253, 253 and 252 files in a 0-255 span). Do not assume `fileId == index` when iterating; read the id list off `GetValidFileIds()`. A dense loop silently misattributes every record after the first gap.

6. Cross-index dependencies, both read-only for a definition editor but needed for any preview: opcode 1 is an index-7 MODEL group id (1785 distinct values, 166 to 63605, against 63614 model groups), and opcode 2 is an index-20 ANIMATION id (1979 distinct, 86 to 15259, against 15260 animation files). Both are well inside range, so nothing here is dangling.

7. No XTEA anywhere on this index, and no unusual compression - all 12 groups are plain GZip with a 2-byte version trailer. The encrypted-versus-not ambiguity that dominates index 5 does not apply.

8. Client naming caution: the constant name GRAPHICS is right in substance but is not what the client calls it, and `RSConstants.GRAPHICS_SHADERS = 31` is an unrelated index. Do not let a `Graphics` identifier collide with `System.Drawing.Graphics` in any WinForms-touching file - same class of build break CLAUDE.md records for `Region`. Name the type `GraphicDefinition` or `SpotAnimDefinition`, never `Graphic`.

9. One genuine unknown: opcode 10 sets `aBoolean909` (`Class107.java:277`) and I found no read of that field anywhere in `Class107`, so what it controls is unknown. It occurs 158 times in this cache and carries no payload, so it costs one byte to round-trip correctly and needs no semantics to encode. Likewise the effect field `aByte923` / `anInt918` (opcodes 9, 11-16) feeds only `Renderable.p(...)`, an abstract method (`Renderable.java:755`); its meaning is unknown and, since none of those opcodes occur here, unknowable from this cache.
