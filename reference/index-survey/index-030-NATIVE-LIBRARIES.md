# Index 30 - NATIVE_LIBRARIES

**Format:** fully-understood  
**Capability:** read-only  
**Effort:** small

## What it is

Index 30 stores the client's platform-native shared libraries as raw binaries, one library per group. Measured from the cache itself: the idx255 table for index 30 is format 6, table version 14, flags 0x03 (identifiers + whirlpool, the only whirlpool table in the cache), 36 groups with contiguous ids 0..35, each holding exactly one file - file id 0 whose own name hash is 0, i.e. the empty string. So group == one library file; file == the whole binary; a record == the library's bytes verbatim. Payload magic across the 36 groups: 13 PE/MZ (groups 0-11 and 32), 15 Mach-O (12-23, 33-35), 8 ELF (24-31). Compression is mixed: 27 GZip and 9 BZip2 (groups 13,14,16,22,25,27,28,30,35); every container carries a 2-byte version trailer. Payload sizes run 14,608 bytes to 3,141,112. The group is addressed by NAME, not by id: the client builds "<os>/<arch>/<libname><ext>" and hashes it. I recovered all 36 names by brute-forcing the stored identifier hashes against NameHasher's algorithm - six library families (jaggl, jagdx, jagmisc, jaclib, hw3d, sw3d) crossed with windows/{x86,x86_64,x64,msjava}, linux/{x86,x86_64}, macos/{universal,x86,x86_64,ppc}, e.g. group 2 = "windows/x86/jaggl.dll", group 25 = "linux/x86/libjaggl.so", group 13 = "macos/universal/libjaggl.dylib". Client authority: InterfaceSettings.java:186 opens index 30 (`Class42_Sub3.openFileStore(-102, true, 1, 30)`); :224 hands that archive to Class365.method3941, which sets Class223.aJS5Archive_1681 and builds the path prefix from os.name and os.arch (Class365.java:44-72). Class35.method337:92-102 concatenates that prefix with Class145.method2315's platform filename ("x.dll" / "libx.so" / "libx.dylib"), looks the group up by name (JS5Archive.method2737/2739 with a file name of ""), and writes the returned byte[] straight to disk via Signlink.method876 (Signlink.java:554-561), then loads it. Proof the file bytes are the binary and nothing else: five DLLs the client already extracted sit in the cache directory, and hw3d.dll/jaggl.dll/jaclib.dll/jagdx.dll/jagmisc.dll are byte-identical to the payloads of groups 1/2/4/5/6.

## Current capability

No index-30-aware code exists anywhere in FlashEditor. The only mention of the index is the constant itself - RSConstants.cs:45 (`NATIVE_LIBRARIES = 30`) and RSConstants.cs:95 (the display-name array). There is no definition class, no decoder, no encoder, no viewer, no export, no import, and no test that names index 30. What works, through the generic layers: (1) READ - `RSCache.ReadFileBytes(30, groupId, 0)` (RSCache.cs:783, over `ReadFile` at :593) returns the library binary exactly; since a record is the raw binary there is nothing further to decode. (2) NAME LOOKUP - `RSReferenceTable.GetArchiveId(name)` (RSReferenceTable.cs:70) already resolves "windows/x86/jaggl.dll" to group 2, because NameHasher.GetNameHash (Cache/Util/NameHasher.cs:51) implements the same `h*31+c` over the lowercased name the client uses, and the index-30 table carries identifiers. (3) SWEEP COVERAGE - index 30 is inside the generic conformance sweeps and, at 36 groups against `SampleArchivesPerIndex = 250` (RealCacheFixture.cs:24), all 36 are covered even in a sampled run: `ArchiveCrcs_MatchTheCapturedContainerBytes`, `Containers_PreserveTheirPayloadAndHeaderAcrossReEncode`, `Archives_ReEncodeToTheCapturedPayloadBytes` and `SingleFileArchives_CarryNoTrailerInTheCapturedBytes` (RealCacheConformanceTests.cs:118, :169, :218, :365) plus `IndexRecords_ReEncodeToTheCapturedBytes` (:479). Note the archive-layer sweep is close to vacuous here - every group is single-file, so encode is a copy. (4) WRITE - `RSCache.WriteFile` (RSCache.cs:102) is generic and would work on index 30, including the whirlpool recompute at RSCache.cs:272-276; nothing has ever exercised it against this index. (5) GUI - the Meta tab's reference-table list (Editor.cs:556, columns at Editor.Designer.cs:355-360) shows index 30's row with the Whirlpool box ticked. That is the entire user-visible surface: no tab shows, extracts or replaces a native library. I verified the write path's riskiest detail against shipped bytes: the 36 stored whirlpool digests match Whirlpool(stored container minus its version trailer) 36 of 36, and 0 of 36 for the full stored bytes or the decompressed payload - which is exactly the span `hashableStream` covers at RSCache.cs:244/274. The CRCs match the same span 36 of 36. Index 30 is the only place in this cache where that branch can be checked at all, and no test checks it.

## Gaps

- A NativeLibraryDefinition (or similar) with Decode/Encode. Decode is identity - the file bytes are the binary - so the class's real job is metadata: split the group name into os/arch/library, classify the payload from its magic (MZ / 7F 45 4C 46 / Mach-O fat CA FE BA BE and thin FE ED FA CE|CF), and read the PE machine word or ELF EI_CLASS so 32- vs 64-bit is shown rather than guessed from the path.
- A committed name table for index 30, the way TrackNames.cs works for index 6/11. The 36 identifiers are name hashes and the table ships no plaintext; without a candidate list the editor can only show a signed integer. The 36 names are fully recovered and can be committed verbatim (see notes), each self-proving because NameHasher.GetNameHash(name) must equal the stored identifier.
- A codec test against captured bytes: commit one small group's container (group 18, 4,224 stored bytes, is the smallest) as a fixture in FlashEditor.Tests/Fixtures/RealCache and assert the payload starts with the right magic and re-encodes unchanged - the same pattern as CapturedCacheBytesTests.
- A full-index byte-identity sweep specific to index 30: for all 36 groups, read the file, WriteFile it back unchanged into a temp copy of the cache, reopen the store (CLAUDE.md: verify persistence by reopening, not by reading back through the cache that wrote it) and assert the payload is unchanged. This is the only sweep that would exercise the whirlpool recompute at RSCache.cs:274, which is currently defended by nothing but the unit tests of the Whirlpool primitive itself (Cache/Util/WhirlpoolTests.cs).
- A reference-table byte-identity check for the whirlpool branch. RealCacheReferenceTableShapeTests only compares LENGTHS (ReferenceTableCodec.Encode(table).ToArray().Length at :217), and the only captured-bytes table fixture is index 28, which has no whirlpool. So ReferenceTableCodec.cs:225-234 - the 64-byte-per-group write - is not proven byte-identical anywhere. Index 30 is the sole table in the cache that can prove it.
- A GUI tab in the Editor.Designer.cs pattern: a TabPage plus an ObjectListView of the 36 groups (name, os, arch, library, format, arch-width, size, compression), an 'Extract' button writing the payload to disk with the correct filename, and an 'Import' button calling cache.WriteFile(RSConstants.NATIVE_LIBRARIES, group, 0, ...). Nothing like it exists - Editor.cs has no SaveFileDialog/OpenFileDialog/File.WriteAllBytes at all, so raw extract/import has to be built from scratch, not copied.

## Notes and traps

TRAPS.

1. THE CACHE CONTRADICTS THE CLIENT ON ONE PATH, AND THE CACHE WINS. Group 11 is the 64-bit Windows jagmisc (PE machine 0x8664, exports Java_jagex3_jagmisc_jagmisc_*, PDB path "P:\\libs_v4s\\jagex3\\run\\jagmisc64.pdb", internal name jagmisc64.dll) and its stored name hash is -157236211, which is hash("windows/x64/jagmisc.dll"). Every other 64-bit Windows library is under "windows/x86_64/" (groups 7,8,9,10,32). Class365.java:70-72 only ever emits "x86_64/" for os.arch amd64|x86_64, so the 637 client asks for "windows/x86_64/jagmisc.dll" - hash 601131542, held by no group - and Class35.method337 returns -1. A 64-bit Windows 637 client therefore cannot load jagmisc from this cache. Do not "fix" the name to match the client; the hash on disk is the fact. It also means a name table must not be generated from the client's prefix rules.

2. THE NAMES ARE THE ONLY ADDRESS, AND THEY ARE NOT IN THE CACHE. Recovered, all 36, each verified by hashing back: 0 windows/msjava/jagmisc.dll, 1 windows/x86/hw3d.dll, 2 windows/x86/jaggl.dll, 3 windows/x86/sw3d.dll, 4 windows/x86/jaclib.dll, 5 windows/x86/jagdx.dll, 6 windows/x86/jagmisc.dll, 7 windows/x86_64/hw3d.dll, 8 windows/x86_64/jaggl.dll, 9 windows/x86_64/jaclib.dll, 10 windows/x86_64/jagdx.dll, 11 windows/x64/jagmisc.dll, 12 macos/universal/libhw3d.dylib, 13 macos/universal/libjaggl.dylib, 14 macos/universal/libjaclib.dylib, 15 macos/x86/libhw3d.dylib, 16 macos/x86/libjaggl.dylib, 17 macos/x86/libjaclib.dylib, 18 macos/x86_64/libhw3d.dylib, 19 macos/x86_64/libjaggl.dylib, 20 macos/x86_64/libjaclib.dylib, 21 macos/ppc/libhw3d.dylib, 22 macos/ppc/libjaggl.dylib, 23 macos/ppc/libjaclib.dylib, 24 linux/x86/libjaclib.so, 25 linux/x86/libjaggl.so, 26 linux/x86/libhw3d.so, 27 linux/x86_64/libjaclib.so, 28 linux/x86_64/libjaggl.so, 29 linux/x86_64/libhw3d.so, 30 linux/x86_64/libsw3d.so, 31 linux/x86/libsw3d.so, 32 windows/x86_64/sw3d.dll, 33 macos/x86_64/libsw3d.dylib, 34 macos/universal/libsw3d.dylib, 35 macos/x86/libsw3d.dylib. There is no linux sw3d for ppc, no macos jagdx/jagmisc, and no linux jagdx/jagmisc - that is the shipped shape, not a gap in the recovery.

3. THE FILE INSIDE THE GROUP IS NAMED "" (hash 0), not by the library filename. A lookup that hashes the filename for the file slot returns nothing. The client passes the empty string explicitly - JS5Archive.method2739 called as method2739(path, "", -32734) at Class35.java:102.

4. WHIRLPOOL IS LIVE ONLY HERE, AND THE SPAN IS THE CRC SPAN. Verified against the shipped digests: 36/36 match Whirlpool(stored container minus version trailer); 0/36 match the full stored bytes and 0/36 the decompressed payload. RSCache.cs:274 already hashes the right span. But because a GZip re-encode is never byte-identical, rewriting a group changes its stored bytes and therefore its CRC and digest legitimately - never diff stored containers to decide whether a save broke something, diff the payload.

5. MIXED COMPRESSION. 9 of the 36 groups are BZip2, the rest GZip; both directions are implemented (RSContainer.cs:146/:200) and the conformance sweep asserts the type survives a re-encode. Do not normalise index 30 to one compressor.

6. NO XTEA anywhere in index 30, and the table is format 6, so there is no per-group flags byte to worry about.

7. The five DLLs loose in the cache directory (hw3d.dll, jaggl.dll, jaclib.dll, jagdx.dll, jagmisc.dll) are the client's own extractions of groups 1,2,4,5,6 and are byte-identical to them. They are excellent free fixtures for a codec test - and a reminder that the cache directory holds client output as well as cache files.

8. DEPENDENCIES: none on other indexes. Index 30 is self-contained. The reverse is not true - ReferenceTableCodec's whirlpool branch and the Editor's Whirlpool column have index 30 as their only real-world exercise, so anything built here should be treated as the regression test for that branch.
